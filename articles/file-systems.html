File Systems: Structure, Implementation & Management

10 min read • File Systems

Introduction

A file system provides a mechanism for storing and organizing data on storage devices. It manages how data is stored, retrieved, and organized, abstracting the physical storage details from users and applications.

What is a File System?

The file system is the component of the OS that manages persistent data storage. It provides a uniform interface to access different storage devices and handles naming, access control, and data organization.

File Concept

What is a File?

  • Named collection of related information
  • Stored on secondary storage (persistent)
  • Smallest logical storage unit from user perspective
  • Can be data (numeric, character, binary) or programs

File Attributes

  • Name: Human-readable identifier
  • Type: Needed for systems supporting different types
  • Size: Current file size
  • Location: Pointer to device and location on device
  • Protection: Access control information (read/write/execute)
  • Time, date, user ID: Creation, last modification, last use

File Operations

create() - Create new file delete() - Remove file open() - Prepare file for access close() - Close file read() - Read data from file write() - Write data to file seek() - Reposition file pointer truncate() - Reset file length to zero append() - Add data to end of file

File Types

  • Regular files: User data (text, binary, executable)
  • Directory files: System files for file organization
  • Special files: I/O devices represented as files (Unix/Linux)

Directory Structure

Single-Level Directory

  • All files in one directory
  • ✅ Simple to implement
  • ❌ Naming conflicts
  • ❌ No grouping capability

Two-Level Directory

  • Separate directory for each user
  • ✅ Isolates users
  • ✅ Avoids naming conflicts
  • ❌ No grouping within user
  • ❌ Difficult to share files

Tree-Structured Directory

  • Most common structure
  • Hierarchical organization
  • Each user has current directory
  • ✅ Efficient searching
  • ✅ Grouping capability
  • ✅ Path names (absolute and relative)
Example Tree Structure: root/ ├── home/ │ ├── alice/ │ │ ├── documents/ │ │ │ └── report.txt │ │ └── pictures/ │ └── bob/ │ └── code/ │ └── main.cpp ├── usr/ │ └── bin/ └── tmp/ Absolute path: /home/alice/documents/report.txt Relative path (from alice/): documents/report.txt

Acyclic Graph Directory

  • Allows sharing of files/directories
  • Uses links (symbolic or hard links)
  • ✅ File sharing
  • ❌ Complexity in traversal and deletion

General Graph Directory

  • Allows cycles
  • Need garbage collection for file deletion
  • Rarely implemented due to complexity

File System Implementation

On-Disk Structures

  • Boot control block: Information to boot OS from volume
  • Volume control block: Volume/partition details (block count, size, free blocks)
  • Directory structure: Organize files
  • File Control Block (FCB): Per-file details (permissions, dates, size, data blocks)

In-Memory Structures

  • Mount table: Information about mounted volumes
  • Directory cache: Recently accessed directory information
  • System-wide open file table: Copy of FCB for each open file
  • Per-process open file table: Pointers to system open file table

Allocation Methods

1. Contiguous Allocation

Each file occupies a set of contiguous blocks on disk.

Example: File A: Blocks 0-4 (5 blocks) File B: Blocks 5-7 (3 blocks) File C: Blocks 8-10 (3 blocks)

Advantages

  • ✅ Simple - only starting location and length needed
  • ✅ Excellent read performance (minimal head movement)
  • ✅ Easy random access

Disadvantages

  • ❌ External fragmentation
  • ❌ Files cannot grow easily
  • ❌ Need to know file size at creation

2. Linked Allocation

Each file is a linked list of disk blocks. Blocks can be scattered anywhere.

Example: File A: Start at block 0 → 3 → 7 → 2 → 11 (end) Each block contains pointer to next block

Advantages

  • ✅ No external fragmentation
  • ✅ Files can grow dynamically
  • ✅ Only starting address needed in directory

Disadvantages

  • ❌ Poor random access (must traverse from beginning)
  • ❌ Pointer overhead in each block
  • ❌ Reliability (broken link = lost file)

Variation: File Allocation Table (FAT)

  • Keep all pointers in a table (FAT) at beginning of volume
  • Used in MS-DOS, Windows 9x
  • ✅ Improves random access
  • ✅ Easier to cache in memory

3. Indexed Allocation

All block pointers are kept in one index block (like a table of contents).

Index Block for File A: [0] → Block 3 [1] → Block 7 [2] → Block 2 [3] → Block 11 [4] → null (end) Directory entry points to index block

Advantages

  • ✅ Supports direct access
  • ✅ No external fragmentation
  • ✅ Dynamic file growth

Disadvantages

  • ❌ Overhead of index block
  • ❌ Wasted space for small files

Handling Large Files

Linked Scheme:

  • Last entry in index block points to another index block

Multilevel Index:

  • First-level index block points to second-level index blocks
  • Similar to paging in memory management

Combined Scheme (Unix inode):

inode contains 15 pointers: Direct blocks (0-11): Point directly to data blocks Single indirect (12): Points to block of pointers Double indirect (13): Points to block of single indirect pointers Triple indirect (14): Points to block of double indirect pointers Handles files from small to very large efficiently!

Free Space Management

1. Bit Vector (Bit Map)

Each block represented by 1 bit: 0 = block free 1 = block allocated Example: 0011101011110000... Blocks 0,1,5,10,11,12,13 are free
  • ✅ Simple and efficient
  • ✅ Easy to find first free block or n consecutive free blocks
  • ❌ Requires extra space
  • ❌ Inefficient unless entire vector in memory

2. Linked List

  • Link all free blocks together
  • Free list head stored in special disk location
  • ✅ No space wasted
  • ❌ Cannot easily get contiguous space
  • ❌ Traversal is time-consuming

3. Grouping

  • First free block stores addresses of n free blocks
  • First n-1 are actually free
  • Last block contains addresses of next n free blocks
  • ✅ Faster than standard linked list

4. Counting

  • Keep address of first free block and count of contiguous free blocks
  • Works well when files allocated contiguously

Disk Scheduling

When multiple requests in disk queue, OS must choose which request to service first.

1. FCFS (First-Come-First-Served)

  • Process requests in order received
  • ✅ Fair
  • ❌ May involve unnecessary head movement

2. SSTF (Shortest Seek Time First)

  • Service request closest to current head position
  • ✅ Better than FCFS
  • ❌ Starvation possible

3. SCAN (Elevator Algorithm)

  • Head moves in one direction servicing requests
  • At end, reverses direction
  • ✅ No starvation
  • ✅ Provides bounded wait time

4. C-SCAN (Circular SCAN)

  • Like SCAN but only services in one direction
  • Returns to beginning without servicing
  • ✅ More uniform wait time

5. LOOK and C-LOOK

  • Like SCAN/C-SCAN but only go as far as last request
  • Don't go to end of disk
  • ✅ Improved performance
Example: Current head at 53 Queue: 98, 183, 37, 122, 14, 124, 65, 67 FCFS: 53→98→183→37→122→14→124→65→67 (640 cylinders) SSTF: 53→65→67→37→14→98→122→124→183 (236 cylinders) SCAN: 53→37→14→0→65→67→98→122→124→183 (236 cylinders)

File System Performance

Buffer Cache

  • Keep frequently accessed blocks in memory
  • Reduces disk I/O
  • Uses LRU or similar replacement

Read-Ahead

  • Anticipate sequential access
  • Pre-fetch next blocks
  • Effective for sequential files

Write Strategies

Synchronous Write:

  • Write immediately to disk
  • ✅ Data safe immediately
  • ❌ Poor performance

Asynchronous Write:

  • Write to cache, flush later
  • ✅ Better performance
  • ❌ Data loss risk on crash

Common Interview Questions

1. What is an inode?

Answer: An inode (index node) is a data structure in Unix/Linux file systems that stores metadata about a file including:

  • File size, permissions, timestamps
  • Pointers to data blocks
  • Does NOT store file name (stored in directory)
Each file has one inode identified by inode number.

2. What's the difference between hard link and soft link?

Answer:

  • Hard link: Multiple directory entries point to same inode. Deleting one doesn't affect others. Can't cross file systems.
  • Soft link (symbolic): Special file containing path to another file. If original is deleted, link breaks. Can cross file systems.

3. Why is contiguous allocation not commonly used?

Answer: Because it causes external fragmentation and requires knowing file size at creation time. Files can't grow easily, making it impractical for modern systems where files change size frequently.

4. What is the purpose of a file allocation table (FAT)?

Answer: FAT is a variation of linked allocation where all block pointers are stored in a table at the beginning of the volume instead of in each block. This improves random access and makes the structure easier to cache in memory.

5. Which disk scheduling algorithm is best?

Answer: LOOK or C-LOOK are generally best for most workloads. They provide good throughput, prevent starvation, and don't waste time going to disk ends. However, real systems may use more sophisticated algorithms considering disk characteristics and workload patterns.

Real-World File Systems

ext4 (Linux)

  • Journaling file system
  • Supports files up to 16 TB
  • Uses extents (contiguous blocks) for better performance

NTFS (Windows)

  • Journaling file system
  • Advanced features: compression, encryption, quotas
  • Uses Master File Table (MFT)

APFS (macOS)

  • Optimized for flash/SSD
  • Space sharing between volumes
  • Snapshots and cloning

Summary

  • File systems manage persistent storage
  • Directories organize files hierarchically
  • Allocation methods: Contiguous (fast but fragmentation), Linked (flexible but poor random access), Indexed (balanced)
  • Free space: Managed via bitmaps or linked lists
  • Disk scheduling: LOOK/C-LOOK commonly used
  • Modern systems: Use journaling for reliability
