Process Synchronization: Semaphores, Mutexes & Monitors

14 min read • Synchronization

Introduction

Process synchronization is crucial in multi-threaded and multi-process systems. When multiple processes/threads access shared data concurrently, we need synchronization mechanisms to ensure data consistency and prevent race conditions.

Why Synchronization?

Without proper synchronization, concurrent access to shared resources can lead to:

  • Race conditions
  • Data inconsistency
  • Unpredictable results
  • System crashes

The Critical Section Problem

What is a Critical Section?

A segment of code where a process accesses shared resources (variables, files, etc.). Only one process should execute in its critical section at a time.

Structure of a Process

do { // Entry Section - Request permission to enter CS // Critical Section - Access shared resource // Exit Section - Release access // Remainder Section - Other code } while (true);

Requirements for Solution

1. Mutual Exclusion

  • Only one process in critical section at a time
  • If process P is in CS, no other process can be in their CS
  • Essential for correctness

2. Progress

  • If no process in CS and some want to enter, selection cannot be postponed indefinitely
  • Only processes not in remainder section can participate in decision
  • Decision must be made in finite time

3. Bounded Waiting

  • Limit on how many times other processes can enter CS after a process requests entry
  • Prevents starvation
  • Ensures fairness

All Three Must Be Satisfied!

A correct synchronization solution must satisfy all three requirements: mutual exclusion, progress, and bounded waiting.

Race Condition

Example: Bank Account

Initial balance = $100 Thread 1: Withdraw $50 Thread 2: Withdraw $30 1. Read balance (100) 1. Read balance (100) 2. Subtract 50 2. Subtract 30 3. Write balance (50) 3. Write balance (70) Final balance could be $50 or $70 (should be $20!) This is a race condition!

The Problem

Operations like "balance = balance - amount" are not atomic. They consist of:

1. LOAD balance into register 2. SUBTRACT amount from register 3. STORE register into balance If these are interleaved between threads, inconsistency occurs!

Peterson's Solution

A classic software-based solution for 2 processes (not practical but educationally important).

Shared variables: int turn; // Whose turn to enter CS bool flag[2]; // flag[i] = true means process i ready to enter CS Process i: flag[i] = true; // I want to enter turn = j; // Give turn to other process while (flag[j] && turn == j) ; // busy wait // Critical Section flag[i] = false; // I'm done // Remainder Section

Why It Works

  • Mutual Exclusion: Both processes set turn to different values, only one succeeds
  • Progress: If one process not interested (flag[j]=false), other enters
  • Bounded Waiting: After one process exits, other gets turn

Limitations

  • Only works for 2 processes
  • Busy waiting (wastes CPU)
  • Requires special memory ordering on modern CPUs
  • Not used in practice

Semaphores

A synchronization tool provided by the operating system. Most widely used synchronization mechanism.

What is a Semaphore?

  • Integer variable accessed via two atomic operations
  • wait() (also called P() or down())
  • signal() (also called V() or up())

Operations

wait(S) { while (S <= 0) ; // busy wait S--; } signal(S) { S++; } These operations are ATOMIC (indivisible)!

Types of Semaphores

1. Binary Semaphore (Mutex)

  • Value can be 0 or 1
  • Used for mutual exclusion
  • Similar to a lock
Semaphore mutex = 1; // Initialize to 1 Process: wait(mutex); // Critical Section signal(mutex); // Remainder Section

2. Counting Semaphore

  • Value can range over unrestricted domain
  • Used to control access to resource with multiple instances
  • Example: Pool of database connections
Semaphore resource = 5; // 5 instances available Process: wait(resource); // Acquire one instance // Use resource signal(resource); // Release instance

Solving Producer-Consumer with Semaphores

Semaphore mutex = 1; // Mutual exclusion Semaphore empty = N; // Count empty slots Semaphore full = 0; // Count full slots Producer: while (true) { // Produce item wait(empty); // Wait for empty slot wait(mutex); // Enter CS // Add item to buffer signal(mutex); // Exit CS signal(full); // Increment full count } Consumer: while (true) { wait(full); // Wait for full slot wait(mutex); // Enter CS // Remove item from buffer signal(mutex); // Exit CS signal(empty); // Increment empty count // Consume item }

Implementation Without Busy Waiting

typedef struct { int value; struct process *list; // Queue of waiting processes } semaphore; wait(semaphore *S) { S->value--; if (S->value < 0) { add this process to S->list; block(); // Put process to sleep } } signal(semaphore *S) { S->value++; if (S->value <= 0) { remove a process P from S->list; wakeup(P); // Wake up the process } }

Mutex Locks

Simplified version of binary semaphore provided by many systems.

bool locked = false; acquire() { while (locked) ; // busy wait locked = true; } release() { locked = false; } Usage: acquire(); // Critical Section release();

Spinlock vs Mutex

  • Spinlock: Busy waits (spins). Good for short critical sections. Used in OS kernels.
  • Mutex with blocking: Puts process to sleep. Good for longer critical sections. Used in applications.

Monitors

High-level synchronization construct that provides a convenient and effective mechanism for process synchronization.

What is a Monitor?

  • Collection of procedures, variables, and data structures grouped in a module
  • Only one process can be active in monitor at a time
  • Mutual exclusion is automatic (enforced by compiler)
  • Used in Java (synchronized methods), C# (lock statement)

Condition Variables

Used to wait for certain conditions within a monitor.

condition x; Operations: x.wait() - Suspend calling process x.signal() - Resume one waiting process If no process waiting, signal has no effect!

Example: Producer-Consumer with Monitor

monitor ProducerConsumer { int buffer[N]; int count = 0; condition not_full, not_empty; void produce(int item) { if (count == N) not_full.wait(); buffer[count++] = item; not_empty.signal(); } int consume() { if (count == 0) not_empty.wait(); int item = buffer[--count]; not_full.signal(); return item; } }

Java Example

public class BankAccount { private int balance = 0; public synchronized void deposit(int amount) { balance += amount; notify(); // Wake up waiting thread } public synchronized void withdraw(int amount) { while (balance < amount) { try { wait(); // Wait until balance sufficient } catch (InterruptedException e) {} } balance -= amount; } }

Classical Synchronization Problems

1. Readers-Writers Problem

Multiple readers can read simultaneously, but writers need exclusive access.

Semaphore mutex = 1; // Protect read_count Semaphore wrt = 1; // Writer lock int read_count = 0; // Number of readers Writer: wait(wrt); // Write data signal(wrt); Reader: wait(mutex); read_count++; if (read_count == 1) wait(wrt); // First reader blocks writers signal(mutex); // Read data wait(mutex); read_count--; if (read_count == 0) signal(wrt); // Last reader allows writers signal(mutex);

Starvation Issue

This solution can starve writers if readers keep arriving. Need to add fairness mechanism!

2. Dining Philosophers Problem

5 philosophers sit around a table. Each needs 2 forks to eat. How to prevent deadlock?

Problem: If all pick up left fork simultaneously → Deadlock! Solution 1: Allow max 4 philosophers to sit Solution 2: Pick up forks only if both available (atomic) Solution 3: Odd philosophers pick left first, even pick right first Solution 4: Use semaphore for each philosopher

3. Sleeping Barber Problem

Barber shop with waiting room. Barber sleeps when no customers, wakes when customer arrives.

Semaphore customers = 0; // Number of waiting customers Semaphore barber = 0; // Barber ready Semaphore mutex = 1; // Protect waiting room int waiting = 0; Barber: while (true) { wait(customers); // Sleep if no customers wait(mutex); waiting--; signal(barber); // Ready to cut signal(mutex); // Cut hair } Customer: wait(mutex); if (waiting < CHAIRS) { waiting++; signal(customers); // Wake barber signal(mutex); wait(barber); // Wait for barber // Get haircut } else { signal(mutex); // Leave (shop full) }

Common Pitfalls

1. Deadlock with Semaphores

Process P0: Process P1: wait(S); wait(Q); wait(Q); wait(S); ... ... signal(Q); signal(S); signal(S); signal(Q); If P0 gets S and P1 gets Q → DEADLOCK!

2. Incorrect Order of Operations

WRONG: signal(mutex); // Exit CS wait(mutex); // Enter CS Critical section not protected!

3. Missing signal()

wait(mutex); // Critical Section // Forgot signal(mutex)! All other processes will block forever!

4. Priority Inversion

Low priority process holds lock needed by high priority process, while medium priority processes run.

  • Solution: Priority inheritance - temporarily boost low priority process

Common Interview Questions

1. What is the difference between mutex and semaphore?

Answer:

  • Mutex: Binary (locked/unlocked). Ownership - same thread must lock and unlock. Used for mutual exclusion.
  • Semaphore: Can be counting. No ownership - any thread can signal. Used for signaling and resource counting.

2. What is a spinlock and when should it be used?

Answer: Spinlock busy-waits instead of sleeping. Use when:

  • Critical section is very short
  • In kernel mode where sleeping is expensive
  • On multiprocessor systems
Don't use for long critical sections (wastes CPU).

3. Explain the producer-consumer problem.

Answer: Producer produces items into bounded buffer, consumer consumes from buffer. Need synchronization to:

  • Prevent producer from adding when buffer full
  • Prevent consumer from removing when buffer empty
  • Ensure mutual exclusion when accessing buffer
Use 3 semaphores: mutex (mutual exclusion), empty (count empty slots), full (count full slots).

4. What is priority inversion?

Answer: When a high-priority task is blocked waiting for a resource held by a low-priority task, while medium-priority tasks run. Solution: priority inheritance or priority ceiling protocol.

5. What are the requirements for a critical section solution?

Answer: Must satisfy three requirements:

  • Mutual Exclusion: Only one process in CS at a time
  • Progress: Selection of next process cannot be postponed indefinitely
  • Bounded Waiting: Limit on number of times others can enter before a waiting process

Summary

  • Synchronization is essential for concurrent programming
  • Critical section problem: Requires mutual exclusion, progress, bounded waiting
  • Semaphores: Most widely used, can be binary or counting
  • Mutex: Simplified binary semaphore with ownership
  • Monitors: High-level construct, automatic mutual exclusion
  • Classical problems: Readers-writers, dining philosophers, sleeping barber
  • Modern languages: Provide built-in synchronization (synchronized in Java, lock in Python)
