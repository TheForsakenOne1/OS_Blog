Inter-Process Communication: Pipes, Messages & Shared Memory

9 min read • IPC

Introduction

Inter-Process Communication (IPC) allows processes to exchange data and synchronize their actions. Modern systems require processes to cooperate and communicate efficiently to accomplish complex tasks.

Why IPC?

Processes need IPC for:

  • Information sharing (shared data)
  • Computation speedup (parallel processing)
  • Modularity (divide system into modules)
  • Convenience (multiple tasks simultaneously)

IPC Models

1. Shared Memory

  • Processes share a region of memory
  • Very fast (no kernel involvement after setup)
  • Requires synchronization by processes
  • Example: POSIX shared memory

2. Message Passing

  • Processes communicate by exchanging messages
  • Slower (kernel involved in each message)
  • Easier to implement (no synchronization needed)
  • Works well in distributed systems
  • Example: Pipes, message queues, sockets
Aspect Shared Memory Message Passing
Speed Fast (direct memory access) Slower (system calls)
Synchronization User's responsibility Handled by OS
Setup Complex initial setup Simpler
Data Size Efficient for large data Better for small messages
Distributed Systems Difficult Natural fit

1. Pipes

One of the earliest and simplest IPC mechanisms. Acts as a conduit allowing two processes to communicate.

Ordinary Pipes (Anonymous Pipes)

  • Unidirectional communication (one-way)
  • Parent-child relationship required
  • Cannot be accessed outside creating process
  • Example: Unix/Linux pipe | operator
Unix/Linux Example: ls | grep txt ls writes to pipe, grep reads from pipe C Code: int fd[2]; // File descriptors: fd[0] for read, fd[1] for write pipe(fd); // Create pipe if (fork() == 0) { // Child process close(fd[0]); // Close read end write(fd[1], "Hello", 5); close(fd[1]); } else { // Parent process close(fd[1]); // Close write end read(fd[0], buffer, 5); close(fd[0]); }

Characteristics

  • Buffer has limited capacity (typically 4KB - 64KB)
  • Blocking: Reader blocks if pipe empty, writer blocks if pipe full
  • Data flows in one direction
  • For bidirectional communication, need two pipes

Named Pipes (FIFOs)

  • Bidirectional communication possible
  • No parent-child relationship required
  • Persists in file system
  • Multiple processes can use
Unix/Linux Named Pipe: Creating FIFO: mkfifo myfifo Writer process: int fd = open("myfifo", O_WRONLY); write(fd, "message", 7); close(fd); Reader process: int fd = open("myfifo", O_RDONLY); read(fd, buffer, 7); close(fd);

Advantages & Disadvantages

  • ✅ Simple to use
  • ✅ Built into shell
  • ✅ Automatic synchronization
  • ❌ Linear data flow only
  • ❌ Limited to local machine (ordinary pipes)
  • ❌ Unidirectional (ordinary pipes)

2. Message Queues

Queue of messages in kernel managed by OS. Processes can send and receive messages.

How It Works

  • Messages stored in queue within kernel
  • Each message has type/priority
  • Processes can select messages by type
  • Messages persist until read or queue deleted
POSIX Message Queue Example: Create queue: mqd_t mq = mq_open("/myqueue", O_CREAT | O_RDWR, 0644, NULL); Send message: char msg[] = "Hello World"; mq_send(mq, msg, strlen(msg), 0); Receive message: char buffer[100]; mq_receive(mq, buffer, 100, NULL); Close and unlink: mq_close(mq); mq_unlink("/myqueue");

Features

  • Asynchronous communication (sender doesn't wait)
  • Message boundaries preserved
  • Can set message priorities
  • Multiple readers/writers possible

Advantages & Disadvantages

  • ✅ Asynchronous - sender doesn't block
  • ✅ Message boundaries maintained
  • ✅ Priority-based messaging
  • ✅ Multiple readers/writers
  • ❌ Size limitations
  • ❌ Kernel resources consumed
  • ❌ Need cleanup (can leak if not removed)

3. Shared Memory

Fastest IPC method. Processes share a region of memory for communication.

How It Works

  • OS allocates a memory segment
  • Multiple processes map it into their address space
  • Direct memory access (no copying)
  • Processes must synchronize access
POSIX Shared Memory Example: Create shared memory: int fd = shm_open("/myshm", O_CREAT | O_RDWR, 0666); ftruncate(fd, SIZE); Map to address space: char *ptr = mmap(0, SIZE, PROT_READ | PROT_WRITE, MAP_SHARED, fd, 0); Writer process: sprintf(ptr, "Hello from writer"); Reader process: printf("%s", ptr); Cleanup: munmap(ptr, SIZE); shm_unlink("/myshm");

Synchronization Required

Problem without synchronization: Writer: Reader: 1. Read count (0) 2. Increment (1) 1. Read count (0) // Wrong! 3. Write (1) Solution: Use semaphores or mutexes! sem_t *sem = sem_open("/mysem", O_CREAT, 0666, 1); Writer: sem_wait(sem); // Modify shared memory sem_post(sem); Reader: sem_wait(sem); // Read shared memory sem_post(sem);

Advantages & Disadvantages

  • ✅ Fastest IPC (no data copying)
  • ✅ Efficient for large data
  • ✅ No kernel involvement after setup
  • ❌ Requires explicit synchronization
  • ❌ Not suitable for distributed systems
  • ❌ Complex error handling

4. Sockets

IPC mechanism for network communication (local or remote).

Types of Sockets

1. Stream Sockets (TCP)

  • Connection-oriented
  • Reliable, ordered delivery
  • Used for most network applications

2. Datagram Sockets (UDP)

  • Connectionless
  • Unreliable, unordered
  • Faster, used for streaming, gaming

3. Unix Domain Sockets

  • Local machine only
  • Faster than network sockets
  • Similar API to network sockets
TCP Socket Example: Server: int server_fd = socket(AF_INET, SOCK_STREAM, 0); bind(server_fd, (struct sockaddr *)&address, sizeof(address)); listen(server_fd, 3); int client_fd = accept(server_fd, NULL, NULL); read(client_fd, buffer, 1024); close(client_fd); Client: int sock = socket(AF_INET, SOCK_STREAM, 0); connect(sock, (struct sockaddr *)&serv_addr, sizeof(serv_addr)); send(sock, "Hello", 5, 0); close(sock);

Advantages & Disadvantages

  • ✅ Works across networks
  • ✅ Flexible (local or remote)
  • ✅ Supports multiple connections
  • ✅ Bidirectional
  • ❌ More complex than other IPC
  • ❌ Overhead (even for local communication)

5. Signals

Software interrupts for notifying processes of events.

Common Signals

SIGINT (2) - Interrupt (Ctrl+C) SIGTERM (15) - Termination request SIGKILL (9) - Force kill (cannot be caught) SIGSEGV (11) - Segmentation fault SIGCHLD (17) - Child process terminated SIGUSR1 (10) - User-defined signal 1 SIGUSR2 (12) - User-defined signal 2

Signal Handling

C Example: void handler(int signum) { printf("Caught signal %d\n", signum); } int main() { signal(SIGINT, handler); // Register handler // Send signal to process kill(pid, SIGUSR1); // Wait for signal pause(); return 0; }

Characteristics

  • Asynchronous (can arrive anytime)
  • Limited information (just signal number)
  • Can interrupt system calls
  • Some signals cannot be caught (SIGKILL, SIGSTOP)

Advantages & Disadvantages

  • ✅ Lightweight
  • ✅ Good for notifications
  • ✅ Built into OS
  • ❌ Limited data transfer
  • ❌ Can be lost if not handled
  • ❌ Difficult to use correctly

Choosing the Right IPC Mechanism

Use Pipes when: - Simple parent-child communication - Shell pipelines - Sequential data flow Use Message Queues when: - Asynchronous communication needed - Message priorities required - Multiple senders/receivers - Messages need to persist Use Shared Memory when: - High-performance required - Large data transfer - Frequent communication - Processes on same machine Use Sockets when: - Network communication - Client-server architecture - Distributed systems - Need connection-oriented protocol Use Signals when: - Simple notifications - Event handling - Process control (terminate, suspend)

Common Interview Questions

1. What's the difference between pipe and named pipe?

Answer:

  • Pipe (anonymous): No name, parent-child relationship required, exists only while processes using it
  • Named Pipe (FIFO): Has a name in file system, no relationship required, persists until explicitly deleted, can be bidirectional

2. Why is shared memory faster than message passing?

Answer: Shared memory avoids copying data. After initial setup, processes access memory directly without kernel involvement. Message passing requires kernel to copy data from sender to kernel to receiver, involving multiple system calls and data copies.

3. What are the drawbacks of shared memory?

Answer:

  • Requires explicit synchronization (semaphores, mutexes)
  • Race conditions if not synchronized properly
  • Only works on same machine (not distributed)
  • More complex error handling
  • Debugging is harder

4. When would you use message queue over shared memory?

Answer: Use message queues when:

  • Processes are unrelated (not parent-child)
  • Messages need to persist
  • Asynchronous communication required
  • Message priorities needed
  • Simpler programming model desired (no manual synchronization)

5. What's the difference between SIGTERM and SIGKILL?

Answer:

  • SIGTERM (15): Polite request to terminate. Process can catch, cleanup, and exit gracefully. Can be ignored.
  • SIGKILL (9): Force kill. Cannot be caught or ignored. Process terminated immediately by OS. No cleanup possible.

Best practice: Try SIGTERM first, use SIGKILL only if process doesn't respond.

Real-World Examples

Pipes

  • Unix/Linux shell pipelines: cat file.txt | grep "error" | wc -l
  • ffmpeg video processing pipelines

Message Queues

  • RabbitMQ, Apache Kafka for distributed systems
  • Windows message loops in GUI applications

Shared Memory

  • Database systems (shared buffer pools)
  • Real-time systems (sensor data sharing)
  • X Window System (graphics rendering)

Sockets

  • Web servers (HTTP communication)
  • Chat applications
  • Database client-server

Signals

  • Process managers (systemd, supervisord)
  • Shell job control (Ctrl+C, Ctrl+Z)
  • Daemon reload configuration (SIGHUP)

Summary

IPC mechanisms enable process cooperation:

  • Pipes: Simple, sequential, great for shell pipelines
  • Message Queues: Asynchronous, persistent, priority-based
  • Shared Memory: Fastest, requires synchronization
  • Sockets: Network-capable, flexible, widely used
  • Signals: Lightweight notifications, limited data

Choose based on requirements: speed, synchronization complexity, data size, and whether communication is local or distributed.
